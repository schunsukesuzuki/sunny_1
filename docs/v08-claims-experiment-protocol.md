# v0.8 実験プロトコル — 要件が間違っていた場合の閉ループ

## 研究仮説

R0は到着順FIFOを厳密に実装できており**実装は正しい**。ところが、期限超過の削減が顧客の本当の目的なら、その要件は十分でない。SIM-SLA-001という**模擬**顧客の反証を与えたQwenは要件欠陥を識別し、要件更新（人間承認）後に生成されたR1実装が、新規HOLDOUTで固定KPIの改善を示せるか。

## シナリオと固定条件

- クライアント：ドイツの保険業務SaaS（架空）。
- 制約：担当資格、案件所要時間、1日あたりのシフト容量、ケースを二重割当しないこと、人間による保険金支払判断。
- デフォルト：3名、4日、18ケース。各seedごとに入力ケースの処理時間、請求額EUR、優先度、期限を変化させる。
- 依頼：予定シフト時間を増やすことなく期限超過を減らす。評価器は**実働時間も同一か**を確認。
- 模擬顧客反例：FIFOが遅い期限の案件を先に処理し、短納期の案件が遅延する。
- 共通評価：遅延+未処理の件数、期限内率、処理済みケース数、割当実働時間、制約違反。

## 手続き

1. **初期設計**：固定されたR0要件を確認。必要ならQwenでサービス設計案生成。人間未承認のドラフトとして保管。
2. **R0技術評価**：FIFOをE2Bで実行し独立評価する。期限優先参照方式も同じseed群で比較。R0が要求を満たしていればPASS。
3. **対照/介入**：顧客反証無しのcontrolではQwenは`insufficient_evidence`と答えるべき。反証有りなら`requirement_mismatch`を推奨し、`SIM-SLA-001`を引用するべき。
4. **人間承認**：固定R1要件とサービス設計を確認し、承認者と理由を記録。証拠は実顧客ではないため要件妥当性の承認ではなく技術実験の承認。
5. **R1コード生成**：Qwenが標準ライブラリのみで新しいPythonコードを生成。
6. **DEV選択・修正**：新しいseed群（初期seed+100～+102）で独立評価。資格・容量違反、期限超過などの集計をQwenへ戻して最大2回修正。**HOLDOUTは一切参照しない**。
7. **HOLDOUT**：有効な候補を選択後、初期seed+20000/+20001の新しいseedで**1回だけ**試す。承認IDごとに一度の評価を強制。実行失敗時は原因を解消し、新たな実験/承認から再試行する。
8. **監査**：結果と要件・サービス設計・実装・独立評価器の契約ID/ハッシュを記録しレポート生成。

## 明確な合格条件

- R0の仕様忠実性がPASS。
- Qwenの分類が`requirement_mismatch`、SIM-SLA-001の引用、期限優先への要件変更を含む。
- R1のHOLDOUT各seedでhard constraintsを全て満たす。
- R1の期限超過が各seedでR0以下、少なくとも1seedで厳密に改善。
- R1の割当審査時間が各seedでR0と完全に同一。
- 実顧客の証拠を得るまでは`business_requirement_validity=UNVERIFIED`。

## 注意

これは外側ループの**技術的成立性**を評価するための意図的な反例です。平均請求審査コスト、実際の負荷分布、人間が考える緊急度、保険商品の特性、法令に適した行動が証明されたわけではありません。比較に使う期限優先の参照方式はヒューリスティックであり、厳密DP/最適化と呼んではいけません。
